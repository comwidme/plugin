# 업무 자동화 상담

이용자의 업무 자동화 요청을 4단계(질문 → 제안 → 설계 → 확인)로 진행한다. 각 단계를 건너뛰지 않는다.

## 1단계. 질문

아래 항목을 표준 질문 세트로 사용한다. 이용자 상황에 따라 일부만 물어도 된다. 한 번에 다 묻지 말고 필요한 만큼만 확인한다.

| 항목 | 확인 내용 |
|---|---|
| 반복 빈도 | 하루/주 몇 회 발생하는 작업인지 |
| 트리거 조건 | 특정 이벤트 발생 시 실행되는지, 정해진 시각에 실행되는지 |
| 실행 주체 | 사람이 확인 후 실행하는지, 완전 자동으로 실행되는지 |
| 사용 데이터/도구 | 파일, 이메일, 채팅, 외부 서비스 등 무엇을 다루는지 |
| 리스크 허용도 | 실패 시 단순 알림 누락 정도인지, 되돌리기 어려운 결과(잘못된 발송·삭제)인지 |

## 2단계. 제안

1단계 답변을 바탕으로 자동화 방안을 제안한다.

- **옵션 수**: 상황이 단순하면 1개를 강하게 추천한다. 상황이 복잡하거나 트레이드오프가 뚜렷할 때만 최대 3개까지 제시한다. 무조건 여러 개를 채우지 않는다.
- **각 옵션에 포함할 내용**: 적용 기능, 예상 효과, 구현 난이도.

기능 선택은 아래 매핑표를 기준으로 한다.

| 상황 | 적용 기능 |
|---|---|
| 같은 규칙을 반복해서 지적/정정해야 함 | CLAUDE.md |
| 같은 절차를 반복해서 요청하게 됨 | Skill |
| 매번 예외 없이 실행돼야 함(린트, 위험 명령 차단 등) | Hook |
| 외부 서비스(DB, Slack, Gmail 등) 접근이 필요함 | MCP |
| 정해진 시각/주기로 실행되어야 함 | Scheduled task (Routine) |
| 많은 파일 검토·리서치처럼 컨텍스트 격리가 필요함 | Subagent |
| 여러 서브에이전트로 대규모 작업(감사, 마이그레이션)을 처리해야 함 | Dynamic workflow |
| 위 컴포넌트 여러 개를 묶어 여러 프로젝트/팀에 재사용해야 함 | Plugin |

## 3단계. 설계

이용자가 선택한 방안으로 설계한다. 애매한 부분은 추가 질문으로 확인한다.

설계안에 반드시 포함할 항목:

- 동작 방식 (트리거 → 처리 → 결과)
- 실패 처리 방안 (오류 발생 시 어떻게 되는지)
- 되돌리기(rollback) 방안 — 특히 Hook처럼 예외 없이 실행되는 기능은 오작동 파급력이 크므로 필수
- 완료 후 검증 방법 (자동화가 의도대로 동작했는지 확인하는 절차)

설계안 문서는 [design-template.md](design-template.md) 형식을 따른다.

## 4단계. 확인 후 진행

- 설계안을 **md 파일로 작성**해 이용자에게 전달한다. 대화로만 설명하고 넘어가지 않는다.
- 이용자 승인을 받은 뒤에만 실제 구현(Skill/Hook/MCP 작성 등)을 진행한다.

## 향후 확장 고려사항

기본은 Skill 단위로 구현한다. 아래 조건이 충족되면 Plugin 전환을 이용자에게 제안한다.

- 이 절차에 Hook, MCP 연동 등 컴포넌트가 추가로 필요해질 때
- 동일 세트를 여러 프로젝트/팀에 재사용해야 할 때
